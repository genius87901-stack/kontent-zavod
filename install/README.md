# Слой установки «Контент-завода» (OWNER)

Каталог `install/` — слой коробки, которым владеет ветка OWNER (CONTRACT.md §5).
Здесь мастер установки `/install` (скилл — в `skills/install/`), его
вспомогательные скрипты и **канонический ридер конфига** для всех модулей.

## Стандарт вызова doctor (контракт запуска)

Каждый модуль проверяется командой:

```
python -m <name>.doctor
```

- запускается из **корня установки**, с каталогом `modules/` (и корнем) на
  `PYTHONPATH`; интерпретатор — из локального `.venv`, если он есть;
- модуль лежит в `modules/<name>/` и является Python-пакетом (`__init__.py` +
  `doctor.py`); имя пакета совпадает с командой `doctor` в манифесте;
- код возврата `0` — полностью работоспособен; `≠0` — урезанный режим либо не
  готов, а на stdout **по-русски** сказано, что не так и как починить (не
  стектрейс). CONTRACT.md §2.

Агрегатор — `run_doctors.py` (честно исполняет команду `doctor` из манифеста,
подменяя `python` на интерпретатор `.venv`).

## Контракт чтения конфига — `factory_config`

Единый ридер для всех модулей. Модуль **не** пишет свою функцию чтения `.env`
или `config.json`, а импортирует общий:

```python
from factory_config import load, get, get_secret, gdrive_root

cfg    = load("publishing")          # dict несекретных ответов клиента
group  = get("vk_group_id")          # одно несекретное значение (или None)
token  = get_secret("vk_token")      # секрет из окружения/.env (или None)
drive  = gdrive_root()               # Path к <GoogleDrive>/КонтентЗавод (или None)
```

Путь до КОНКРЕТНОЙ папки контракта (`1 Сырьё`, `2 На утверждение`, …) даёт не
этот ридер, а `modules.intake.drive_layout.folder_paths()` — там же лежит и сам
контракт (`drive_structure.json`), единый источник имён папок. `gdrive_subdir()`
раньше указывал на структуру Диска до её пересборки (`Загрузить/Готово/
Опубликовано`) и был удалён 11.08.2026 как мёртвый код без вызовов — задним
числом её всё равно никто не звал.

### API

| Функция | Что делает |
|---|---|
| `root(start=None)` | Path корня установки. Ищет маркер `.factory_root` (создаёт установщик), иначе запасные (`config/`, `modules/`, `CONTRACT.md`); можно переопределить переменной окружения `FACTORY_ROOT`. |
| `load(module_name=None, *, refresh=False)` | dict из `config/factory.config.json` (несекретные ответы). Ключи глобальны; `module_name` пока справочный. Нет файла → `{}`. |
| `get(key, default=None)` | Одно несекретное значение по ключу (без учёта регистра). |
| `get_secret(key)` | Секрет по ключу вопроса. Ищет в окружении и `.env` без учёта регистра, мостит имена (`vk_token` ↔ `VK_TOKEN`). Нет → `None`. Значение не логируется. |
| `has_secret(key)` | `True/False`. |
| `gdrive_root()` | Path к `<gdrive_root>/КонтентЗавод` или `None`. |

### Где что лежит (относительно корня установки)

```
<root>/.factory_root              — маркер корня (создаёт установщик)
<root>/config/factory.config.json — несекретные ответы клиента
<root>/.env                       — секреты (0600, gitignored)
<root>/modules/<name>/            — модули с манифестом и doctor
<root>/.venv/                     — локальное окружение (в git не идёт)
```

### Мост имён ключей (важно)

- Ключи вопросов канонизируются в `lower_snake_case`; дедуп вопросов — **без
  учёта регистра** (`upload_post_api_key` и `UPLOAD_POST_API_KEY` — один вопрос).
- Секреты в `.env` хранятся в `UPPER_SNAKE`. При импорте `factory_config`
  подмешивает `.env` в `os.environ` (не перетирая заданное), поэтому и новый
  `get_secret()`, и легаси-код `os.environ.get("VK_TOKEN")` видят одно и то же.
  Это позволяет модулям мигрировать на общий ридер постепенно.

## Поэтапная установка (3 этапа под интенсив)

Клиент разворачивает завод **не разом, а тремя последовательными этапами** — по ходу
интенсива. Раскладка «этап → модули/скилы» задаётся в **`stages.json`** (правит только
OWNER), пройденные этапы запоминаются в **`install/.state.json`** (идемпотентность и
докат). Мастер `/install` ставит ровно один этап за прогон и помнит, что уже стоит.

| Этап | Что включает | Что даёт клиенту |
|---|---|---|
| **1. Смыслы и база** | распаковка смыслов как ФУНДАМЕНТ (скилл `self_unpacking` для живой сессии + DIY `ученикам/02_РАСПАКОВКА_ВОПРОСЫ.md`), окружение, приём материалов (intake, папки Google Диска), движок каруселей (engine-media), клиентские скилы контента (content-interface) | распаковать смыслы, кидать фото/видео в Google Диск, делать первые карусели НА смыслах |
| **2. Reels и публикация** | разговорные/виральные форматы (viral-formats), публикация с предохранителем (publishing) | собирать Reels/разговорные ролики и публиковать по команде |
| **3. Продвинутое** | виральная разведка (niche-hooks), авто-сторис (story-publisher) | разведка конкурентов, автосторис |

**Смыслы — фундамент, не финал.** По офферу Валерии распаковка смыслов — шаг 1: без неё
завод рендерит красивые карусели ни о чём, а карусели/Reels строятся НА смыслах. Поэтому
слой смыслов вынесен в **этап 1** и делается ПЕРВЫМ (до каруселей). Нюанс: `self_unpacking`
— это **живая сессия Валерии** (созвон, не self-install шаг), поэтому этап 1 даёт два пути:
(а) скилл `/self_unpacking` для сессии с Валерией; (б) ссылку на self-serve распаковку
`ученикам/02_РАСПАКОВКА_ВОПРОСЫ.md` для DIY. Поле `first_step` этапа 1 в `stages.json`
несёт этот текст, мастер `/install` озвучивает его с нажимом.

Модуль **атомарен**: его pip ставится целиком на его этапе. `engine-media` содержит и
рендер каруселей, и рендер Reels; карусели (первый продукт) уже требуют его движков,
поэтому вся `engine-media` ставится на этапе 1. Reels технически доступны сразу, но
интенсив ведёт клиента: этап 1 — смыслы и карусели, этап 2 — Reels/публикация/разговорные
форматы поверх уже стоящего движка. Раскладку можно менять в `stages.json` (если, например,
`engine-media` позже разделят на два модуля — это решает его владелец).

Имена модулей в `stages.json` сопоставляются с `manifest.name` / именем каталога **без
учёта регистра и дефис↔подчёркивание** (`niche-hooks` == `niche_hooks`). Модули, которых
ещё нет в дереве (до слияния сборки), тихо пропускаются.

| Скрипт | Шаг | Роль |
|---|---|---|
| `stages.py` | 0–1, 8 | Политика этапов (`stages.json`) и состояние (`.state.json`): `--status`/`--json` (что стоит, что дальше), `--resolve "этап 2"\|next` (номер этапа), `--mark-done N`. |
| `check_env.py` | 2 | Проверка Python/git; ffmpeg НЕ обязателен (движок берёт `imageio-ffmpeg`). |

| `make_venv.py` | 4 | Локальный `.venv` + один `pip install` по плану этапа; проверка `==`; `requirements.lock.txt`. |
| `setup_config.py` | 5–6 | Пишет `config/factory.config.json` (**сливая** с прошлыми этапами) + `.env` (0600), маркер, папки модулей этапа и структуру Google Диска. Отсутствующий файл ответов = пустые ответы. |

| `factory_config.py` | рантайм | Канонический ридер (выше). В коробке копируется в корень установки. |

## Отдельный шаг установки «музыка» (банк треков, вне этапов 1–3)

Банк музыки под Reels (~49 треков) — это **МЕДИА, а не код**, поэтому он **не входит в
базовый клиентский `.zip`**: в архиве на его месте пустая папка-приёмник `music/.keep`
(как у `photos`/`video`/`stock`). Так стартовый архив остаётся лёгким. Музыка
доустанавливается **отдельным, необязательным шагом** — по желанию клиента.

- **Описание шага** — в `install/stages.json`, ключ `optional_steps` (id `music`): не
  входит в сквозную нумерацию этапов и в `next`-цепочку, этапы не блокирует. Мастер
  `/install` видит его в `stages.py --status`/`--json` и предлагает по запросу
  («доустанови музыку»), запуская `python install/install_music.py`.
- **Откуда берётся музыка (источник по приоритету):** `--src ПУТЬ` → переменная
  `FACTORY_MUSIC_SRC` → ключ `music_src` в `config/factory.config.json`. На **dev-машине
  владельца** источник — локальная папка/симлинк с банком (у владельца `music/` смотрит в
  его Google Drive). У **клиента** источника обычно нет — базовый архив приезжает с пустым
  `music/`: тогда шаг **не падает и НЕ качает из сети**, а подсказывает положить свои
  лицензионные треки (`.mp3/.m4a/.wav/.aac/.ogg/.flac`) в папку `music/`.
- **Аддитивно и идемпотентно:** копирует только недостающие треки (сверка по имени),
  повтор безопасен.
- **Из сети — ничего молча:** скрипт только копирует локальные файлы. Завод работает и
  **без** банка: движок подбирает музыку сам через Openverse (`music.py`).

## Корневые файлы движков в коробке (`ROOT_FILES_BY_MODULE`)

Модули в дереве «тонкие» (`module.manifest.json` + `doctor.py`), а рабочий **код движков**
лежит плоско в **корне** репозитория (`engine_*.py`, `talk_*.py`, `render_reels.py`,
`checks.py`, `music*.py`, `stock.py`, `broll_index.json`, `fonts/`; `import_photos.py` для
intake; `autopost.py`/`vk*`/`tg_send.py` для publishing). В коробке он тоже обязан лежать в
**корне установки** — `doctor`'ы модулей ищут его как top-level import (напр.
`modules/engine_media/doctor.py` делает `import talk_transcribe`). `build_box` кладёт эти
файлы в корень архива по **белому списку** `ROOT_FILES_BY_MODULE` (OWNER-дефолт); владелец
модуля может переопределить список ключом `root_files_in_box` в своём манифесте. Дев-обвязка
(`board*`, `sync_*`, `factory_web`, `build_c*/r*`, `caption_*`, `.env`, …) в список не входит
и в коробку не попадает.

## Модуль `niche-hooks` (виральная разведка) в коробке

Сам инструмент — скилл `skills/niche-hooks/SKILL.md` (ручная разведка через vidIQ MCP +
`/watch` + `yt-dlp`). Его **модульный паспорт** — `modules/niche_hooks/`
(`module.manifest.json` + `doctor.py`) — ставится на **этапе 3**. Требования к клиенту:

- **vidIQ MCP** — главный источник данных; подключается в Claude Code, программно из
  Python не проверяется (`doctor` только напоминает о нём и о трате кредитов).
- **Экономика vidIQ — на аккаунте КЛИЕНТА.** vidIQ работает на **личном аккаунте клиента
  и его кредитах** — это отдельная платная регистрация, которую клиент заводит сам. **Наши
  MCP-креды в коробку не едут** (иначе разведка тратила бы наши деньги). Это скрытая
  стоимость — она честно проговорена в `stages.json` (этап 3, `warnings`), клиентском
  `CLAUDE.md`, `КАК_УСТАНОВИТЬ.md` и выводе `doctor`.
- **yt-dlp + ffmpeg + скилл `/watch`** — нужны для разбора YouTube/TikTok. Их наличие
  `doctor` проверяет и по-русски объясняет, чего не хватает; разведка Instagram через
  vidIQ работает и без них (урезанный режим). `yt-dlp` заявлен как мягкий `system_binaries`
  (`winget install yt-dlp.yt-dlp`).

Это **ручной** инструмент: тратит платные кредиты vidIQ, в авто-пайплайн не встраивается.
`build_box` теперь **включает** niche-hooks в клиентский zip (раньше исключал).

## Какие скилы едут клиенту (allowlist, не «скопом»)

`build_box` кладёт в коробку **только явно помеченные** клиентские скилы — по флагу
`ships_to_client: true` во фронтматтере `SKILL.md`. **Дефолт — НЕ едет:** новый внутренний
OWNER-скил не утечёт клиенту сам собой (это была бы регрессия). Помечены как клиентские:
`install`, `niche-hooks`. Скилы, чей `SKILL.md` **вне зоны редактирования OWNER** (напр.
`self_unpacking` — владелец content-interface), но которые должны ехать, перечислены в
`SHIP_SKILLS_ALLOWLIST` внутри `build_box.py`; их владелец добавит флаг во фронтматтер, и
тогда строку из allowlist можно убрать.

## Границы (CONTRACT.md §3)

Без абсолютных путей (всё от корня по маркеру). Без `input()` в модулях. Секреты
только вне git. pip только с `==`. Без AGPL. Рантайм — кроссплатформенный Python
(целевая ОС клиента — Windows), без bash-измов.
