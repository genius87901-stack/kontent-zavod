# DESIGN — модуль `analytics` (аналитика опубликованного контента + рекомендации)

> Задача доски **BOX-15**. Аддитивный модуль-CONSUMER: ничего в корне не
> переписывает, движок (`engine_*`, `render_reels`, `checks`) и чужие модули не
> трогает, предохранитель публикации не ослабляет. Ничего не публикует и не
> тратит платные API. Ветка `agent/box15`. Пишет только в `modules/analytics/` и
> в свою папку данных `analytics/`.

## 1. Зачем

Завод умеет придумать, собрать и опубликовать контент. Не хватает последнего
звена — **обратной связи**: что из вышедшего сработало, а что нет, и что с этим
делать. Эксперт (Валерия) не должен вручную сводить цифры из Insights площадок и
гадать. Модуль `analytics`:

1. собирает метрики **уже вышедших** постов (охваты, показы, досмотр/удержание,
   реакции, сохранения, репосты, переходы по ссылке);
2. считает производные ставки (досмотр, вовлечённость, сохранения, CTR);
3. по **детерминированным правилам** превращает метрики в конкретные советы
   «что поменять в следующем посте».

Он замыкает цепочку завода в петлю: `content_plan` → `script_writer` →
`engine_talk`/`render_reels` → `publishing`/`story_publisher` → **`analytics`** →
подсказки обратно в `content_plan` (см. §6).

## 2. Источник за флагом: образец по умолчанию, живой Upload-Post при ключе

**Живой сбор идёт через Upload-Post — тот же сервис, что публикует контент**
(`autopost.py` / модуль `publishing`). У него же есть аналитика вышедших постов,
поэтому отдельные токены Insights каждой площадки не нужны — хватает уже
настроенного для публикации ключа `UPLOAD_POST_API_KEY`.

Флаг `analytics_metrics_source`: `sample` (по умолчанию, безопасно, ничего не
зовёт) / `upload_post` (живой сбор; `live` — исторический синоним). **Живой путь
идёт в платный сервис ТОЛЬКО при наличии ключа**: без ключа `fetch_metrics` честно
берёт образец из карточки поста и объясняет это по-русски — чужой аккаунт вслепую
не жжётся (`BOX-19`). Весь остальной каркас (нормализация, хранилище, ставки,
правила, рекомендации, петля обратной связи) вход-агностичен и работает одинаково
на образце, живом ответе и ручной выгрузке.

**Раскладку полей** можно проверить бесплатно и без ключа — публичный
`GET /api/uploadposts/platform-metrics` (`python -m analytics.cli probe`): он
отдаёт главное поле показов по каждой площадке (у площадок оно разное), а
`upload_post.impressions_field_map()` превращает это в карту, которую `normalize`
использует для заполнения показов.

**Вход-агностик.** Движок рекомендаций не знает и не хочет знать, откуда пришли
метрики: образец, живой Insights или ручная выгрузка. Между источником и правилами
стоит единый нормализованный вид метрик (`model.METRIC_FIELDS`).

## 3. Как устроено (файлы)

| Файл | Роль |
|---|---|
| `config.py` | единственная точка чтения конфига (пороги, источник) — зеркалит контракт `content_plan`/`script_writer`; секретов нет, всё от корня установки через pathlib |
| `paths.py` | пути данных модуля; `ensure_dirs()` кладёт `.gitignore` с `*` — метрики аккаунта клиента не уезжают в репозиторий |
| `model.py` | схема метрик, производные ставки (`derive`), json-хранилище (атомарная запись), базовая линия охвата (медиана), валидация |
| `providers.py` | **абстракция источника**: провайдер на площадку (IG/TG/VK) с `normalize(raw, field_map)`; `fetch_metrics(post, live, field_map)` — единая точка входа; `fetch_live` — живой сбор через Upload-Post по `request_id`/`platform_post_id`, БЕЗ ключа/идентификатора → `LiveSourceUnavailable` (откат на образец, платный аккаунт не трогаем) |
| `upload_post.py` | тонкий клиент Upload-Post (только stdlib `urllib`): чтение ключа как в publishing (env→`.env`, не логируется), эндпоинты по посту/кэшу/профилю/суммарным показам, публичный `platform-metrics` (без ключа), разбор ответа (`platform_block`, `impressions_field_map`) |
| `recommender.py` | **детерминированные правила** «метрика→совет» + LLM-хук `llm_advice` (заглушка) + свёртка в подсказки планировщику |
| `questions.py` | список вопросов диалога (задаёт Claude Code, не модуль — `input()` запрещён) |
| `cli.py` | ручной прогон: `questions / example-metrics / ingest / list / recommend / feedback` |
| `doctor.py` | проверка rc=0, по-русски, без стектрейсов |
| `metrics.sample.json` | образец-mock (коммитится, как `brief.example.json`) |

**Модель метрик** — единый нормализованный вид, поля-`None`, если площадка такого
не отдаёт (не `0`!): `reach, impressions, views, avg_watch_sec, video_len_sec,
retention_pct, likes, comments, saves, shares, forwards, profile_visits,
link_clicks, follows`. Провайдеры переводят «сырьё» площадки в этот вид:
- **IG** — богатейший набор (охват, плеи, среднее время просмотра, сохранения,
  переходы по ссылке `website_taps`);
- **TG** — просмотры, реакции (→ `likes`), пересылки (→ `forwards`), клики;
  охвата/сохранений в IG-смысле нет → `None`;
- **VK** — просмотры, лайки, комментарии, репосты (→ `forwards`), клики.

**Производные ставки** (`model.derive`) считаются от базы аудитории (охват →
показы → просмотры, первое доступное): досмотр (`avg_watch/len` или прямое
значение площадки), вовлечённость, доля сохранений, CTR. Чего не хватает данных —
`None`, и правило на этой метрике тактично молчит.

**Детерминизм** — главное свойство: одни метрики → один набор советов. Никакой
случайности, никакой сети. Хранилище — обычный json в своей папке, запись
атомарная (`.tmp` → `replace`).

## 4. Правила «метрика → совет»

Каждое правило — порог на нормализованной ставке + человеческий совет с
**конкретным действием** + `planner_hint` (см. §6). Пороги читаются из конфига, но
имеют валидные умолчания — модуль работает без единой настройки.

| Правило | Условие (умолчание) | Совет |
|---|---|---|
| `low_retention` | досмотр < 35 % | усилить хук в первые 3 сек, сократить ролик |
| `low_ctr` | переходы/охват < 1 % | явный CTA + кодовое слово, ссылка в первый комментарий |
| `low_saves` | сохранения/охват < 1.5 % | добавить пользу-выжимку (чек-лист/цифры) |
| `low_engagement` | реакции/охват < 5 % | вопрос/провокация/голосование |
| `weak_reach` | охват < медианы на 30 % | проверить время выхода и обложку/первые секунды |
| `scale_winner` | всё в норме | повторить тему/формат, масштабировать в план |

Правило охвата требует **истории ≥ 3 постов** по этой площадке+формату (медиана) —
иначе честно молчит: на одном посте «средний охват» не посчитать. Это прямой
маркер того, где нужны накопленные живые данные (§7).

## 5. LLM-хук и оценка сложности

Точка «умного» шага — `recommender.llm_advice(record, base_block, generate=None)`,
по образцу `planner.llm_ideas` / `writer.llm_script`:

- **по умолчанию** (`generate=None`) возвращает детерминированную базу как есть —
  платный API и сеть НЕ трогаются;
- расширение включается, только если **ведущий явно** передаёт
  `generate(record, base_block) -> list[str]`, который где-то снаружи (отдельная
  задача) обратится к модели и вернёт дополнительные текстовые советы;
- шов безопасный: строки подмешиваются как советы уровня `low`, сбой/мусор → тихо
  остаёмся на базе. Никакого сетевого кода в модуле нет.

**Что даст модель:** объяснить *почему* пост просел словами эксперта, связать
несколько метрик в одну гипотезу, предложить точную переформулировку хука под
конкретную тему. База даёт правила-пороги; LLM — интерпретацию поверх них.

**Оценка подключения живого LLM-хука: ~6–9 часов** (промпт под метрики + few-shot
на голосе книги смыслов; structured-output и merge поверх базы; рельсы качества;
офлайн-тесты фолбэка; переключатель источника).

## 6. Петля обратной связи с планировщиком (planner НЕ трогаем)

`recommender.planner_feedback(blocks)` сворачивает советы всех постов в **подсказки**
для `content_plan.planner`:
- `scale_up` — какие рубрики/форматы **зашли** (правило `scale_winner`) → в план
  их больше;
- `fix_repeating` — какие проблемы **повторяются** (низкий досмотр, мало переходов)
  → в план поправку: усилить хук на этой рубрике, ставить явный CTA.

Это записывается в **свой** файл `analytics/planner_feedback.suggest.json`
(`cli feedback`). **Важно:** модуль `analytics` **НЕ импортирует и НЕ вызывает**
`content_plan.planner` — граница владения по файлам чистая. Как planner мог бы это
учитывать в будущем (отдельная задача на стороне `content_plan`, не здесь):

- на входе `planner._build_idea_pool` подмешивать вес рубрикам из `scale_up`
  (чаще ставить зашедшие темы) — ровно та точка, куда уже вынесен `llm_ideas`-хук;
- в бриф слота класть пометку `fix: strengthen_hook`, которую `script_writer`
  прочитал бы как приоритет хука.

Направление данных — только `analytics → файл-подсказка`. Никаких обратных
импортов, никакого обхода предохранителя публикации.

## 7. Живой сбор через Upload-Post и шов с публикацией

Живой драйвер реализован: `upload_post.py` + `providers.fetch_live` тянут метрики
через Upload-Post (эндпоинты сверены по docs.upload-post.com):

- **Пачка снимков (основной путь):** `GET /api/uploadposts/post-analytics/cached?
  user=…[&platform&limit&cursor&since&until]` — снимки метрик постов из кэша
  сервиса. Площадки при этом **не дёргаются**, поэтому лимита «100 запросов /
  5 минут» на нём НЕТ. Отдаёт до 200 постов за запрос: весь `ingest` — это один-два
  сетевых вызова, а не по вызову на пост.
- **Связь с нашей публикацией:** `GET /api/uploadposts/status?request_id=…` —
  отсюда берём **нативный id и ссылку** вышедшего поста.
- **Профиль (живо, тратит лимит):** `GET /api/analytics/{profile_username}?
  platforms=…`. Вынесен в отдельную команду `cli profile`, в общий `ingest` не
  входит: он дёргает сами площадки и расходует лимит 100 запросов / 5 минут.
- **Журнал сервиса (запасной путь):** `GET /api/uploadposts/history?page=&limit=`.

**Исправление прошлой версии модуля (BOX-19).** Раньше здесь были записаны
эндпоинты `post-analytics/{request_id}`, `platform-metrics` и
`total-impressions/{profile}`. Сверка с `openapi.json` показала: **таких путей в
API нет**. Поэтому:

- связь «наш `request_id` → метрики» строится в ДВА шага (status → нативный
  id/ссылка → поиск в пачке `cached`), это и делает `live.LiveSession`;
- карта «главное поле показов у площадки» стала **локальной фикстурой**
  (`fixtures/platform_metrics.sample.json`, читает `providers.load_field_map`) —
  по сети за ней ходить некуда;
- заголовок авторизации шлём сразу в двух видах: `Authorization: Apikey <ключ>`
  (так ходит боевой `autopost.py`) и `X-API-Key: <ключ>` (так объявлено в спеке).
  Лишний заголовок сервис игнорирует, а мы не зависим от того, какая схема жива.

Ключ читается **как в publishing** (env → `.env` корня установки), в код/лог не
пишется. Площадки: Upload-Post покрывает IG/TG (и др. соцсети); **VK сервисом не
покрывается** (`PLATFORM_MAP["vk"] = None`) — по VK живого источника нет, честный
откат на образец/ручную выгрузку.

### Лестница деградации: модуль не имеет права упасть

Аналитика — сетевая функция, но клиент работает на Windows и часто офлайн.
Поэтому любой сбой спускается на ступень ниже, всегда с причиной по-русски:

| Ступень | `source` | Когда |
|---|---|---|
| живой ответ | `upload_post` | всё хорошо |
| последний успешный ответ из кэша | `upload_post_cache` | сети нет / API упал, но кэш есть |
| образец / ручная выгрузка | `sample` | кэша тоже нет, но в карточке есть `raw` |
| честное «данных нет» + причина | `ok=False` | нет вообще ничего |

Что именно обеспечивает устойчивость:

- **Ретраи с бэкоффом** (`upload_post._request`): повторяем ТОЛЬКО поправимое —
  сеть/таймаут, `429`, `5xx`; пауза `1.5 * 2^n` + джиттер, потолок 20 с. Отказ
  ключа (`401/403`), `404` и битый JSON НЕ повторяем: ожиданием это не чинится, а
  лишние повторы жгут лимит чужого аккаунта.
- **Таймауты**: 20 с на запрос, максимум 3 страницы пачки за прогон.
- **Кэш последнего успешного ответа** (`cache.py` → `analytics/live_cache.json`)
  плюс отметка `last_success` — по ней `doctor` и `cli status` отвечают на вопрос
  «а живой сбор вообще хоть раз сработал и когда».
- **Нет ключа → в сеть не идём вообще** (проверено тестом: список вызовов пуст).
- **Нет ключа связи у поста** (ни `request_id`, ни ссылки) → за этим постом в сеть
  тоже не идём.

### Шов с публикацией по `request_id` — ЗАКРЫТ

`autopost.persist_published` пишет `.state/published_ids.jsonl` — по строке на
площадку с полями `request_id / platform / user / post_id / material /
media_type / published_at / status`. Модуль этот журнал **только читает**
(`published.py`) и превращает в карточки постов, которые идут в живой сбор.
Поэтому `ingest` по умолчанию берёт список постов из журнала публикаций, а на
образец откатывается, только если журнала нет (или указан `--sample`).

### История: динамика, а не только срез

`model.py` хранит СРЕЗ (одна запись на пост, upsert по `post_id`). Для вопросов
«пост ещё набирает или встал?» этого мало, поэтому каждый успешный замер
дополнительно дописывается в `analytics/metrics_history.jsonl` (`history.py`):
по строке JSON на «пост × момент замера». Одинаковый снимок подряд не пишется —
ежечасный прогон не раздувает файл нулевой динамикой. Смотреть:
`python -m analytics.cli history [--post ID] [--field views]`.

JSONL, а не sqlite: модуль обязан остаться на чистом stdlib и переживать обрыв
записи — битая строка при чтении просто пропускается.

- **Накопленная история** — правило `weak_reach` и тренды требуют ≥ 3–10 постов на
  площадку+формат. Пока история не набрана, часть правил молчит — честное «данных
  ещё мало».

До наполнения живыми данными модуль работает на образце и ручной выгрузке
(`example-metrics` → заменить `raw` → `ingest`). Переключение — один флаг
`analytics_metrics_source`, остальной код не меняется.

## 8. Границы и предохранители (CONTRACT.md §3)

- Абсолютных путей нет — всё от корня установки (каталог с `CONTRACT.md`) через
  `pathlib`. `input()` нет — параметры через argparse/конфиг, вопросы — через
  `config_questions` манифеста и `questions.py`. Секретов нет; токены живого
  источника (будущее) читались бы из окружения. `pip: []` (только stdlib).
  AGPL-зависимостей нет. Bash-измов в рантайме нет (целевая ОС — Windows).
- Ничего не публикует, `--send` не зовёт. Живой сбор — через Upload-Post и
  **только при наличии ключа**; без ключа честный откат на образец
  (`LiveSourceUnavailable`), платный аккаунт вслепую не трогается. Аутентифи-
  цированный вызов уходит лишь по явному `request_id`/`platform_post_id` поста.
- Рантайм-метрики аккаунта клиента гитигнорятся: `ensure_dirs()` кладёт в папку
  данных `.gitignore` с `*`. В репозиторий из модуля уезжает только код и
  образец `metrics.sample.json`.
- Движок, чужие модули, `CONTRACT.md`, `BOARD.md` не трогаются. Реестровую строку
  §5 в контракт вписывает ведущий (см. §9).

## 10. Проверки («замер, не вывод»)

- `python -m analytics.doctor` → **rc=0** (пороги, предохранитель живого
  Upload-Post: без ключа/без `request_id` платного вызова нет, чтение образца,
  сквозной прогон нормализация→запись→рекомендации, хранилище).
- `python -m analytics.test_live` → **офлайн-тесты живого сбора на записанных
  ответах API** (52 проверки): разбор `cached`/`status`, ответ → нормализованные
  метрики, устойчивость (нет ключа / нет сети / 401 / 429 / 5xx / пустой ответ /
  битый JSON), ретраи и бэкофф, кэш, история, шов с публикацией. Транспорт
  подменён — **ни одного сетевого байта и ни одного платного вызова**.
- `python -m analytics.cli probe` → сухой прогон живого сбора БЕЗ сети: какие
  посты годятся, по какому ключу связи и сколько запросов это породит.
- `python -m analytics.cli status` → состояние живого сбора без сети: форма ключа
  (сам ключ не печатается), профиль, журнал публикаций, когда было последнее
  успешное обновление живых данных.
- `python -m analytics.cli ingest [--live]` → снимает посты в хранилище и
  дописывает замер в историю (при `--live` без ключа/сети — честный откат).
- `python -m analytics.cli history` → динамика метрик между замерами.
- `python -m analytics.cli recommend` → печатает советы по постам (замер ниже).
- `python -m analytics.cli feedback` → сворачивает в подсказки планировщику (файл).
- Самолинт запретов: `grep -rnE "input\(|/Users/|C:\\\\|AGPL" modules/analytics/`
  → только строки-комментарии про сам запрет.
