# DESIGN — модуль `script_writer` (генератор сценариев съёмки Reels)

> Задача доски **BOX-13**. Аддитивный модуль-CONSUMER: ничего в корне не
> переписывает, ядро (`engine_*`, `talk_*`, `render_reels`, `checks`) не трогает,
> предохранитель публикации не ослабляет. Ничего не публикует и не тратит платные
> API. Ветка `agent/box13`.

## 1. Зачем

Эксперт (Валерия) идёт снимать разговорный Reels — и ему нужен не «пост», а
**подсказка на съёмке**: что именно сказать и что показать, по кадрам. ПРОМТ 2 в
`ПРОМТ_КОНТЕНТ.md` уже описывает это словами («хук на экране, 4–5 битов текста, к
каждому визуальная подсказка, финальный бит CTA»). Этот модуль превращает ПРОМТ 2
в **детерминированный код-генератор**: строка контент-плана → готовый сценарий по
дублям, который эксперт держит в руках у камеры.

Он замыкает цепочку завода: `content_plan` (BOX-11) раскладывает план →
`script_writer` (BOX-13) разворачивает строку плана в сценарий съёмки →
`engine_talk`/`render_reels` монтируют снятое видео → `caption_bridge` (BOX-10)
пишет подпись. Каждое звено — свой модуль, свои файлы.

## 2. Вход и выход

**Вход** — одна единица под съёмку (ровно строка плана ПРОМТ 2):
`рубрика | тема | (опц.) хук | (опц.) кодовое слово` + книга смыслов проекта
(`CONTENT_BIBLE_*.md`, тот же источник, что у `content_plan`). Читается своим
кодом (`bible.py`) — граница владения по файлам чистая.

**Выход** — сценарий в трёх видах (папка `script_writer/output/`):
- `<slug>.txt` — голый текст **на руки на съёмке** (без разметки);
- `<slug>.md` — разбор для человека (дубли, чек-лист, правила качества);
- `<slug>.json` — машинный вид (для будущей автоподачи в движок).

**Простой дубль** (по просьбе эксперта). Каждый дубль несёт ровно то, что нужно на
съёмке: `say` (что сказать), `show` (что показать/перебивка), `duration_sec`
(длительность), `subtitle` (субтитр). Раскладку монтажа и тип плана камеры из
дубля **убрали** — эксперту нужен простой сценарий «сказать/показать», а не
режиссёрский план. Служебно остаются: `intent` (hook/point/emotion/cta —
таксономия `talk_plan`, держит арку и валидацию) и `visual_query` (англ. запрос к
стоку — задел под автоподбор перебивки, в человекочитаемый вывод не печатается).
Первый дубль — **хук**, последний — **CTA с кодовым словом**.

## 3. Как устроено

**Драматургическая арка** (из шаблона книги смыслов «30 сценариев прогрева»):

```
ХУК → … (боль / ошибка / кейс / инсайт / возможность) … → CTA
```

Средних битов 3–5 (по умолчанию 4). Хук и CTA — всегда. Порядок средних битов
задаёт **выбранная арка** (§4, левер 3), а не фиксированный список. Реплики
берутся из банка `_RUBRIC_LINES` (7 рубрик × 5 стадий) — сжатая выжимка книги
смыслов с реальным якорем-активом («136 точек роста»), написанная **нейтрально по
роду** и в настоящем времени, поверх которой подмешиваются реальные фразы книги
(§4, левер 1). Глубокую пере-персонализацию реплик делает LLM-хук (см. §5).

**Детерминизм** — главное свойство: одни входные данные → один и тот же сценарий.
Никакой случайности, никакой сети. Любой выбор из банков (арка, хук, реальная
фраза) идёт по **устойчивому md5-хешу темы** (а не по `hash()`, который
рандомизирован `PYTHONHASHSEED`). Длительность раскладывается по весам стадий
методом наибольших остатков — сумма всегда равна заданной длине ролика.

**Урезанный режим без падений** (CONTRACT.md §1): нет книги смыслов → фразы из
общих заготовок, `bible_ok=false`, doctor честно предупреждает — но сценарий всё
равно собирается. Неизвестная рубрика → нейтральный `_FALLBACK_LINES`.

## 4. Три рычага качества без платного ИИ

Всё офлайн и детерминированно; при отсутствии книги/банка — мягкий фолбэк.

**Левер 1 — реальные фразы книги смыслов.** `bible.py` дополнительно парсит секцию
«100 ТЕМ ДЛЯ ПОСТОВ» в `themes` = {рубрика → [реальные фразы]}. Эти формулировки
клиента идут (а) в пул **хука** и (б) в биты `ошибка`/`возможность` (реплика «его
голосом»). Кейс всегда опирается на якорный факт книги. Нет тем → заготовки
`_RUBRIC_LINES`.

**Левер 2 — виральные хуки разведки.** Если на диске есть банк `/niche-hooks`,
`writer._niche_hooks()` читает его через `content_plan.niche_bridge.load_triples`
(**только чтение** готового .md-банка) и подмешивает реально залетевшие первые
фразы в пул хука с приоритетом. Нет банка / модуль недоступен → `[]`, тихо, без
сети и без запуска разведки.

**Левер 3 — ротация драматургических арок.** Вместо одной арки на всё — банк
`_ARCS` (5 порядков средних битов); арка выбирается детерминированно по теме
(`_pick_arc`, md5). Инвариант: `case` (доказательство) стоит в первых трёх
позициях каждой арки, поэтому при любом N битов (3–5) кейс в сценарии есть и
смысловая логика хук → … → кейс → CTA сохраняется.

| Арка | Порядок средних битов |
|---|---|
| `classic` | боль · ошибка · кейс · инсайт · возможность |
| `proof_first` | кейс · боль · ошибка · инсайт · возможность |
| `provocation` | ошибка · кейс · боль · возможность · инсайт |
| `story` | боль · кейс · инсайт · ошибка · возможность |
| `contrast` | ошибка · боль · кейс · возможность · инсайт |

## 5. LLM-хук и оценка сложности

Точка «умного» шага — `writer.llm_script(brief, base_script, generate=None)`,
по образцу `planner.llm_ideas` / `caption_bridge.llm_caption`:

- **по умолчанию** (`generate=None`) возвращает детерминированную базу как есть —
  платный API и сеть НЕ трогаются;
- расширение включается, только если **ведущий явно** передаёт
  `generate(brief, base_script) -> dict`, который где-то снаружи обратится к
  модели и вернёт улучшенный сценарий того же формата;
- шов безопасный: результат модели прогоняется через `model.validate`, мусор/сбой
  → тихо остаёмся на базе. Никакого сетевого кода в модуле нет.

**Что даст модель:** пере-написать реплики под конкретную тему дословно (сейчас
база даёт рубричную арку, тему вплетает в хук/кадр), подобрать более острый хук,
подстроить род под эксперта.

**Оценка подключения живого LLM-хука: ~8–12 часов.**
- 2–3 ч — промпт под схему дубля + few-shot на голосе книги смыслов;
- 2–3 ч — structured-output и merge поверх базы (валидация схемы уже есть);
- 2 ч — рельсы качества (запрет выдуманных цифр, красные линии, суммы не называем);
- 2–3 ч — офлайн-тесты детерминизма фолбэка и мок-`generate`;
- 1 ч — переключатель источника (env/конфиг) и документация.

## 6. Границы и предохранители (CONTRACT.md §3)

- Абсолютных путей нет — всё от корня установки (каталог с `CONTRACT.md`) через
  `pathlib`. `input()` нет — параметры через argparse/`brief.json`, вопросы —
  через `config_questions` манифеста и `questions.py`. Секретов нет. `pip: []`
  (только stdlib). AGPL-зависимостей нет. Bash-измов в рантайме нет (Windows).
- Ничего не публикует, `--send` не зовёт, платные API не трогает.
- Рантайм-сценарии (со смыслами клиента) гитигнорятся: `ensure_dirs()` кладёт в
  папку данных `.gitignore` с `*`. В репозиторий из модуля уезжает только код и
  `brief.example.json`.

```
| Сценарии съёмки (script_writer) | Команда «Контент-завод» (ветка agent/box13) | `modules/script_writer/` (manifest + doctor + код). Детерминированный генератор простого сценария разговорного Reels по дублям из строки контент-плана и книги смыслов: что сказать / что показать, длительность, субтитр (без раскладок монтажа и типов плана), хук + CTA с кодовым словом. Качество без ИИ: реальные фразы книги, виральные хуки разведки, ротация арок. Выход .md/.txt/.json. LLM-хук `writer.llm_script` — заглушка, платный API не зовёт. Ничего не публикует. |
```

## 8. Проверки («замер, не вывод»)

- `python -m script_writer.doctor` → **rc=0** (умолчания, книга смыслов, сборка
  тестового сценария + валидация схемы).
- `python -m script_writer.cli write --rubric ... --topic ...` → пишет .md/.txt/.json.
- Самолинт запретов: `grep -rnE "input\(|/Users/|C:\\\\|AGPL" modules/script_writer/`
  → только строки-комментарии про сам запрет.
- Детерминизм, покрытие всех 8 раскладок, валидность 7 рубрик × 3/4/5 битов,
  сумма длительностей == цель, поведение LLM-хука (база / merge / фолбэк на сбое)
  — проверены прогоном.
