# DESIGN — модуль `content_plan` (контент-план + автономный исполнитель + гейт с вето)

> Прототип. Ветка `agent/content-plan`. Аддитивный модуль, ничего в корне не
> переписывает, предохранитель публикации не ослабляет. Реальной автопубликации
> в прототипе НЕТ (жёсткий стоп, см. §5).

## 1. Зачем

Сегодня цикл такой: человек руками собирает пост (`build_*.py` / `render_reels.py`),
руками показывает, руками зовёт `autopost.py --send`. Клиент хочет иначе:

> «Один раз утвердить план на неделю/месяц — и дальше система сама генерит
> контент по плану, а я только могу остановить плохой пост до того, как он уйдёт.»

Модуль добавляет три вещи поверх существующего завода:

1. **Планировщик** — заранее собирает у клиента все вводные под период и
   раскладывает контент-план (дата → формат → тема/смысл → площадки).
2. **Автономный исполнитель** — по плану на каждый созревший слот генерит контент
   существующими движками и кладёт в очередь «готово к публикации».
3. **Гейт публикации с окном-вето** — публикация идёт по расписанию, но каждый
   готовый пост показывается клиенту заранее (за `veto_hours` часов). Не снял —
   уходит по расписанию (с фиксацией в логе). Снял — не уходит.

## 2. Как соблюдён ЗАКОН проекта (предохранитель публикации)

В проекте закон: **ничего не публикуется без слова человека** (предохранитель
`--send` в `autopost.py`/`render_reels.py`). Полностью бесконтрольную
автопубликацию делать нельзя. Модуль НЕ обходит и НЕ трогает этот предохранитель.
Автономность строится не на отключении флага, а на **пред-разрешении + окне-вето**:

- **Слово человека на период = утверждение плана.** Пока `plan.approved != true`,
  исполнитель ничего не генерит, а гейт ничего не публикует. Утверждение —
  это осознанный акт клиента заранее на весь период (его «да» на список слотов).
- **Окно-вето = право отменить каждый конкретный пост.** Готовый слот показывается
  клиенту за `veto_hours` часов до времени публикации. До времени публикации
  клиент может снять слот (`veto`) или поправить (`reslot`). Это и продуктово
  верно: клиент хочет мочь остановить плохой пост.
- **Публикация идёт ТЕМ ЖЕ путём, что требует явного разрешения.** Гейт не пишет
  свой постинг. Он собирает ровно ту команду `autopost.py`, которую человек ввёл
  бы руками, и реальная отправка возможна только через штатный `--send` самого
  `autopost.py` — существующий предохранитель остаётся на месте. Для автономного
  режима «явное разрешение» складывается из двух пред-условий (утверждён план +
  истекло окно-вето без снятия), а не из выключенного флага.
- **Пять замков на реальную отправку** (все обязаны совпасть):
  1. `plan.approved == true` — слово человека на период;
  2. `now >= publish_at` — время выхода наступило, окно-вето истекло;
  3. **слот в статусе `approved`** — конкретный выпуск утверждён: клиент имел
     полный `veto_hours`-интервал, не снял слот, и одобрение зафиксировано
     (в `daily` — руками через `cli approve-slot`, в горизонтных режимах —
     авто-одобрением, которое наступает только по истечении окна);
  4. включён конфиг `content_plan_live_publish == true` **И** запуск гейта явно
     вооружён (`--arm`). Дефолт обоих — выключено (dry-run). Клиент отвечает на
     этот вопрос сам при установке (`config_questions`, дефолт — «нет»);
  5. **у выпуска есть НАСТОЯЩИЙ собранный материал** (`gate.material_ready`):
     включена реальная сборка (`CONTENT_PLAN_REAL_GEN`), у слота нет
     `needs_input`, и в очереди лежит артефакт с `dry_run:false` и непустым
     `media`. Замок закрывает худший исход проекта: сняли стоп публикации, забыв
     включить сборку — и в живые аккаунты клиентов ушли бы заглушки-описания
     вместо постов. Сюда же попадают слоты **сторис**: движка сторис в заводе
     нет, у них всегда `needs_input`, и в `autopost.py` вообще нет режима сторис
     (только `--dir` и `--video`) — такой слот не уйдёт никогда.
- **Жёсткий стоп прототипа.** В коде гейта `REAL_PUBLISH_IMPLEMENTED = False`.
  Даже когда все пять замков совпали и запуск вооружён — гейт НЕ вызывает
  `autopost --send`. Он печатает точную команду, которая ушла бы, и пишет её в
  лог. То есть прототип физически не способен ничего опубликовать. Снять этот
  стоп — отдельная задача интеграции (владелец `autopost.py` — ветка publishing),
  и только вместе с ней подключается настоящий путь.

Итог: клиент утверждает план заранее (его «слово»), система автономно генерит весь
период, публикация по расписанию — но через окно-вето и через штатный
`--send`-путь. Бесконтрольного постинга нет ни в одном режиме.

## 3. Какие вопросы задаём клиенту (интервью планировщика)

`input()` внутри модулей запрещён контрактом — диалог ведёт Claude Code / мастер
установки, зачитывая структурированный список из `questions.py`, а ответы
складывает в `brief.json`. Три параметра-умолчания также вынесены в
`config_questions` манифеста (их спросит установщик).

**Формат вопроса — choice.** У каждого вопроса есть `options` (готовые варианты,
чтобы клиент выбирал, а не сочинял с нуля) и `default` (что взять, если он
сказал «давай как обычно»). Умолчания, у которых есть ключ в конфиге, читаются
из конфига через `config.py`. Вопрос с `strict: True` (режим одобрения) принимает
ТОЛЬКО значения из списка — незнакомый режим молча откатывается на безопасный
`daily`; остальные вопросы мягкие (клиент вправе назвать свою рубрику).

**Переиспользование.** Ответы ложатся в `content_plan/brief.json`, и следующее
интервью подкладывает его базой: клиенту достаточно назвать только то, что он
меняет. Слои складываются так: `умолчания ← прошлый brief.json ← новые ответы`
(`questions.merge_brief`). `--fresh` сбрасывает на умолчания.

```
python -m content_plan.cli questions                       # показать интервью
python -m content_plan.cli interview --set horizon_days=7 \
        --set formats=carousel,reels --set publish_approval_mode=week
python -m content_plan.cli plan --brief brief.json
```

Вопросы под период (полный список — в `questions.py`):

1. **Площадки** — куда публикуем (instagram, telegram, youtube, vk…).
2. **Частота** — сколько постов в неделю.
3. **Горизонт** — на сколько недель/дней планируем вперёд.
4. **Форматы** — карусели, Reels, или чередовать.
5. **Рубрики/темы** — какие смысловые линии крутим (по умолчанию берём из
   Content Bible клиента: точки роста, кейсы, ИИ, мышление, личный бренд,
   продажи, провокации).
6. **Тон** — как звучим (по умолчанию из `ПРОЕКТ.md`: на «ты», мужской род,
   дерзкие хуки, конкретика, без инфоцыганщины).
7. **Ключевые даты / акции** — что нельзя пропустить (запуск, вебинар, дедлайн
   оффера) — под них планировщик ставит отдельные слоты.
8. **Стоп-темы** — о чём НЕ пишем ни при каких условиях.
9. **Время публикации** — во сколько по дням выходим.
10. **Окно-вето** — за сколько часов показывать пост на утверждение/отмену.

## 4. Схема плана (`content_plan.json`)

```json
{
  "version": 1,
  "created": "2026-07-29T12:00:00",
  "approved": false,
  "approved_at": null,
  "approved_by": null,
  "brief": {
    "period": {"start": "2026-08-01", "end": "2026-08-31"},
    "platforms": ["instagram", "telegram"],
    "posts_per_week": 4,
    "formats": ["carousel", "reels"],
    "rubrics": ["Точки роста", "Кейсы", "ИИ", "Провокации"],
    "tone": "на «ты», мужской род, конкретика, без инфоцыганщины",
    "post_time": "10:00",
    "veto_hours": 12,
    "key_dates": [{"date": "2026-08-15", "note": "старт набора на разбор"}],
    "forbidden": ["скидки-обещания дохода", "чужие кейсы без разрешения"]
  },
  "slots": [
    {
      "id": "2026-08-01-carousel-1",
      "date": "2026-08-01",
      "time": "10:00",
      "publish_at": "2026-08-01T10:00:00",
      "format": "carousel",
      "rubric": "Точки роста",
      "topic": "Где чаще всего лежат дополнительные 500 000 ₽",
      "meaning": "показать, что деньги уже в бизнесе — нужен взгляд со стороны",
      "hook": "Где лежат дополнительные 500 000 ₽.",
      "platforms": ["instagram", "telegram"],
      "status": "planned",
      "artifact": null,
      "generated_at": null,
      "veto_opens_at": "2026-07-31T22:00:00",
      "history": []
    }
  ]
}
```

**Статусы слота** (продуктовыми словами — так они и печатаются в таблицах):

| статус | подпись | что значит |
|---|---|---|
| `planned` | черновик | слот стоит в плане, контент ещё не собран |
| `generated` | на утверждении | контент собран, открыто окно-вето, клиент видит |
| `showcased` | в витрине, ждёт просмотра | единица выложена в личный телеграм-канал клиента, он листает её с телефона (BOX-26) |
| `revising` | есть правки от клиента | клиент словами сказал, что переделать. Такой слот НЕ одобряется ни вручную, ни авто |
| `approved` | утверждён | клиент сказал «да» этому выпуску (руками в режиме `daily`, в составе пакета через `approve-package` либо авто-одобрением по истечении окна в горизонтных режимах). Публикации ещё НЕ было |
| `published` | опубликован | ушло наружу. **В прототипе недостижим** — жёсткий стоп |
| `vetoed` | снят | клиент снял выпуск, он не уйдёт |
| `failed` | ошибка | сборка упала; слот можно вернуть в план |

Счастливый путь: `planned → generated → showcased → approved → published`.
Ветки: `revising` (правка от клиента → `generated` после переделки или
`planned` при пересборке), `vetoed` (снять можно и уже утверждённый слот — до
самого выхода), `reslot` (назад в `planned`), `failed`. Переходы — только через
`model.set_status`, каждый пишется в `history`.

`model.PENDING_APPROVAL = (generated, showcased)` — кортеж «ждёт решения
человека»; гейт и витрина обращаются к нему, а не перечисляют статусы руками.
Прямой переход `generated → approved` оставлен намеренно: витрина может быть
недоступна (офлайн-клиент), и тогда клиент утверждает по таблице, как раньше.

Ключевое: **`approved` — отдельный статус, а не побочный эффект времени.** Гейт
пускает в путь публикации только `approved`-слоты. Авто-одобрение (режимы
`week`…`month`) наступает лишь тогда, когда клиент получил ВСЁ окно-вето
(`now >= publish_at`) и не снял слот — иначе пред-разрешение съело бы право
вето, ради которого окно и существует.

## 5. Автономность: как работает исполнитель и гейт

**Исполнитель** (`executor.py`, зовётся из `scheduler.py`):
- берёт слоты, которым пора генериться (за `lead_days` до публикации), статус
  `planned`, план утверждён;
- для каждого зовёт генератор (`generate_slot`) — тонкий шов к существующим
  движкам (`engine*`, `render_reels`, подбор перебивок). **В прототипе генератор
  работает в dry-run**: не запускает движки и не тратит API, а фиксирует, каким
  путём слот собрался бы, и кладёт запись-заглушку в очередь `content_plan/queue/`;
- переводит слот `planned → generated`, проставляет `generated_at` и `veto_opens_at`.

**Гейт** (`gate.py`, зовётся из `scheduler.py`):
- открывает окно-вето: для `generated`-слотов, у которых `now >= veto_opens_at`,
  пишет человекочитаемую доску `veto_board.md` («что скоро уйдёт, можно отменить»);
- на время публикации проверяет пять замков (§2) и — вместо реальной отправки —
  печатает и логирует точную команду `autopost.py`, которая ушла бы. Реального
  постинга нет (`REAL_PUBLISH_IMPLEMENTED = False`).
- всё фиксируется в `publish_log.jsonl` (что, когда, куда, каким решением).

**Расписание.** Цикл (`scheduler.py --loop`) раз в интервал прогоняет
исполнитель + гейт. По умолчанию `--dry-run` и `--once`. В коробке это вешается
тем же подходом, что уже принят в проекте: на Windows у клиента —
Планировщик заданий (schtasks) с командой `python -m content_plan.scheduler --once`
раз в N минут; на маке разработки — launchd (как `sync_daemon`). Модуль не тащит
свой демон-фреймворк и не создаёт служб сам (это слой установки, OWNER).

|---|---|
| `module.manifest.json` | манифест (config_questions, folders, doctor) |
| `doctor.py` | проверка готовности по-русски, код возврата 0/1 |
| `config.py` | единственная точка чтения конфига (зеркало story_publisher) |
| `paths.py` | пути к плану/очереди/логам относительно корня установки |
| `model.py` | схема плана, load/save, статусы и переходы слотов |

| `executor.py` | автономная генерация созревших слотов (dry-run шов к движкам) |
| `gate.py` | окно-вето + путь публикации через autopost (жёсткий стоп) |
| `scheduler.py` | цикл по расписанию: executor + gate; `--once/--loop/--dry-run` |
| `showcase.py` | витрина в личном телеграм-канале клиента: подписи, провайдер отправки, приём правок, одобрение пакета, расписание ежедневной выдачи (BOX-26) |
| `cli.py` | операции человека: interview/plan/status/table/board/approve/approve-slot/veto/reslot + showcase/showcase-status/revise/revise-done/approve-package/delivery (argparse, без input) |

## 6d. Витрина: личный телеграм-канал клиента (BOX-26)

Схема утверждена владельцем и реализована как описана.

1. **Горизонт.** Клиент выбирает срок — неделя / две / три (`brief.horizon_days`).
2. **Весь пакет заранее.** Исполнитель собирает контент на весь период:
   `python -m content_plan.scheduler --once --lead-days <горизонт>`.
3. **Выкладка в витрину.** `cli showcase --send` кладёт каждую единицу в личный
   телеграм-канал клиента ОТДЕЛЬНЫМ сообщением: карусель — альбомом
   (`sendMediaGroup`), рилс — видео (`sendVideo`), несобранный черновик — текстом
   (`sendMessage`). Канал служит и витриной, и архивом всего контента клиента.
   Подпись содержит обязательное: дату планируемой публикации со зоной, площадки,
   рубрику/тему и **служебный идентификатор слота** — по нему клиент сошлётся.
4. **Правки словами.** Клиент листает канал с телефона и возвращается в Claude
   Code: «в ролике за 5 августа переснять хук». Claude фиксирует это командой
   `cli revise --slot <id> --text "..."`. Слот уходит в статус «есть правки от
   клиента» и НЕ одобряется ни вручную, ни авто, пока правку не отработают
   (`revise-done`, при необходимости `--regenerate`). Телеграм — витрина,
   Claude — интерфейс правок.
5. **Одобрение пакета целиком.** `cli approve-package --who "..."` — слово
   человека на весь период. Не проходит, пока есть неготовые или непросмотренные
   единицы: «одобрить всё» должно значить, что человек видел ВСЁ.
6. **Ежедневная выдача.** `cli delivery [--apply]` раскладывает одобренную
   очередь ПО ОДНОЙ ЕДИНИЦЕ В ДЕНЬ в выбранное время. Если единиц больше, чем
   дней горизонта — очередь растягивается и модуль называет дату конца; если
   меньше — прямо говорит, сколько дней останется без контента.

**Время и часовой пояс.** Оба — вопросы клиенту в формате choice
(`post_time`: 09:00 / 12:00 / 18:00 / 21:00 / своё; `post_timezone`: список зон
или своё смещение). Время хранится СО ЗНАЧЕНИЕМ ЗОНЫ (`publish_at_tz`:
`2026-08-05T21:00:00+05:00`), наивное `publish_at` остаётся только для
арифметики гейта на машине клиента. Смещения зашиты таблицей `config.TIMEZONES`,
потому что у клиента Windows без сети, а `zoneinfo` там требует пакет `tzdata`;
если `zoneinfo` доступен — берётся он, таблица запасная. Все перечисленные зоны
летнее время не переводят, так что фиксированное смещение для них точное.

**Провайдер.** Тот же путь, которым завод уже кладёт готовое в телеграм-архив:
прямой Bot API своим ботом (как `tg_send.py`), ключи `TG_BOT_TOKEN` и
`TG_SHOWCASE_CHAT_ID` / `TG_CHAT_ID` — только из `.env`, в коде и в чате их нет.
Через `autopost.py` витрина НЕ идёт намеренно: autopost — это путь ПУБЛИКАЦИИ в
соцсети (Upload-Post) под предохранителем, а витрина — показ клиенту в его
собственном канале, и смешивать их значило бы протащить показ через
предохранитель публикации.

**Предохранители витрины.** (1) Без `--send` — пробный прогон, запрос к Telegram
не делается и статус слота НЕ меняется: клиент ничего не увидел, значит «показано»
врать нельзя. (2) Нет токена/канала/сети/`requests` — модуль не падает, а честно
говорит «витрина недоступна»; план и черновики целы. (3) `CONTENT_PLAN_SHOWCASE_STUB=1`
— заглушка для прогонов на фикстурах: сеть не трогается вовсе, сообщения пишутся
в `content_plan/showcase_stub/`. (4) Витрина НЕ знает про autopost и никогда не
переводит слот в `published` — предохранитель публикации она обойти не может.

## 6a. Что видит человек: таблица плана и доска-вето

План машиночитаемый (`content_plan.json`) и человекочитаемый одновременно:

```
python -m content_plan.cli table --week        # окно 7 дней, таблица в консоли
python -m content_plan.cli table --month --md  # окно 30 дней + content_plan.md
python -m content_plan.cli board               # что сейчас в окне-вето
```

Таблица показывает дата / день недели / время / формат / рубрика / куда / статус
/ тема — то есть ровно «что, когда, куда». `--md` выгружает ту же таблицу в
markdown (`content_plan/content_plan.md`), чтобы её можно было отправить клиенту.
`--start` двигает окно, если нужно посмотреть не первую неделю плана.

## 6b. Форматы и что завод реально умеет

| формат | планируется | собирается автономно |
|---|---|---|
| `carousel` | да | да — `carousel_bridge` → `engine_photo` (сырьё: фото с диска клиента) |
| `reels` | да | да — `reels_bridge` → `render_reels` (сырьё: говорящее видео + перебивки) |
| `stories` | да | **нет** — движка сторис в заводе нет; слот честно уходит в dry-run с `needs_input`, собирается вручную |

Если сырья не нашлось, слот НЕ падает: мост возвращает `needs_input`, слот
получает dry-run-артефакт с пометкой, какой вход нужен, и остаётся в плане.

## 6c. Что проверяет доктор

`python -m content_plan.doctor` (код 0 — готов, 1 — есть что поправить):

1. параметры плана и окна-вето — из брифа собранного плана, а не из умолчаний;
2. **предохранитель**: жёсткий стоп на месте, режим сборки черновиков, режим
   участия клиента (тоже из брифа плана — иначе доктор соврал бы);
3. состояние плана: сколько слотов, утверждён ли;
4. **валидность плана**: даты читаются, id уникальны, у каждого слота окно-вето
   открывается РАНЬШЕ выхода (иначе клиент физически не успеет снять пост), и
   стоп-темы клиента не просочились в темы/крючки слотов (сверка по основам
   слов — русский склоняется, целые слова тут не работают);
5. **хватает ли сырья**: спрашивает мосты (`carousel_bridge.resolve_photos`,
   `reels_bridge.resolve_video`), нашли бы они вход — БЕЗ запуска движков и без
   единого платного вызова. Нет сырья — это `i`, а не ошибка: слоты уйдут в
   dry-run с пометкой, какой вход нужен;
6. **ничего не опубликовано без утверждения** — главный закон. Если при
   включённом жёстком стопе в плане вдруг есть `published`-слоты, это значит,
   что файл плана правили руками: доктор поднимает тревогу и возвращает 1.

## 7. Что осталось на интеграцию (не входит в прототип)

- Подключить реальный генератор в `executor.generate_slot` к движкам
  (`engine*`, `render_reels`, `talk_broll`) — с автоподбором темы→кадра→музыки.
- Снять `REAL_PUBLISH_IMPLEMENTED = False` и подключить настоящий вызов
  `autopost.py --send` — совместно с владельцем `autopost.py` (ветка publishing),
  сохранив штатный `--send`-предохранитель.
- Канал уведомления клиента об открытии окна-вето (сейчас — файл `veto_board.md`;
  в проде — Telegram-бот/доска). Без него режим «молчаливого ухода» опасен.
- Движок сторис: формат планируется, но не собирается (см. §6b).
- Регистрация задания расписания в слое установки (OWNER, `install/stages.json`).

## 8. Риски

- **Дрейф темы.** Автогенерация может повторять смыслы. Митигация: планировщик
  раскладывает рубрики ротацией и не ставит одну тему дважды в окне.
- **Молчаливый уход.** Если клиент не смотрит доску-вето, пост уйдёт по расписанию.
  Это by design (пред-разрешение), но канал уведомления обязателен в проде.
- **Сдвиг ответственности.** Пред-разрешение плана — юридически «слово» клиента;
  формулировка утверждения должна прямо об этом говорить (см. `cli.py approve`).
- **Реальная отправка.** Пока стоит жёсткий стоп — риск нулевой. Снятие стопа —
  только с владельцем autopost и с повторной проверкой предохранителя.
